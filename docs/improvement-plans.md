# Планы улучшения doomraVPN

Дата обновления: 2026-11-09.

**Статус: только план. Реализацию не начинать без отдельного указания пользователя.**

В рамках подготовки этого файла не изменять приложение, действующий VPN, настройки пользователя или VPS; не генерировать ключи, не собирать и не публиковать новые релизы. Задачи ниже описывают будущую работу, а не выполненные изменения.

При последующем выполнении применять `superpowers:executing-plans` либо согласованный процесс реализации. Каждый этап должен иметь проверяемый результат; невыполненные пункты не отмечать завершёнными.

## 1. Обновление установленной Windows x64 версии

### Цель и границы

Реализовать сценарий **Настройки → Проверить обновления → описание новой версии → Скачать → Установить** через существующий установщик Inno Setup.

Проверка и скачивание работают без включённого VPN. Они не запускают VPN-ядра и не отключают активное соединение. Подключение завершается согласованно только при явной установке обновления.

Автоматическая установка относится только к установленной Windows x64 версии. **Portable пока обновляется ручным скачиванием и распаковкой ZIP**, без автоматической замены файлов и без неявного перехода на установленную версию.

Текущая база: версия 0.56 / FileVersion 0.56.0.0; C# 5, WinForms, .NET Framework 4.8; Windows 10/11 x64; Inno Setup 7.1.1. Номер будущего релиза определить перед реализацией, сверившись с актуальной версией проекта.

### Согласованный серверный контракт

| Назначение | Адрес |
|---|---|
| Origin | `https://doomra-vpn.duckdns.org:8443` |
| Манифест | `/windows/x64/stable/latest.json` |
| Подпись | `/windows/x64/stable/latest.json.sig` |
| Пакеты | `/releases/<версия>/<файл>` |

Использовать структуру JSON из отчёта от 2026-11-09:

```json
{
  "schemaVersion": 1,
  "appId": "doomraVPN",
  "channel": "stable",
  "platform": "windows",
  "architecture": "x64",
  "version": "<четырёхкомпонентная версия файла>",
  "displayVersion": "<пользовательская версия>",
  "minimumWindowsVersion": "10.0",
  "requiredDotNetFramework": "4.8",
  "releaseNotes": "<описание изменений обычным текстом>",
  "packages": {
    "installer": {
      "path": "/releases/<версия>/<файл установщика.exe>",
      "size": 0,
      "sha256": "<64 шестнадцатеричных символа>"
    },
    "portable": {
      "path": "/releases/<версия>/<portable-архив.zip>",
      "size": 0,
      "sha256": "<64 шестнадцатеричных символа>"
    }
  }
}
```

Это шаблон, не готовый манифест: заполнители и нулевые размеры должны быть заменены фактическими значениями скриптом публикации. Поле portable сохраняется для ручного скачивания. Дату публикации и дополнительные поля не вводить без согласования изменения схемы.

### Подпись и ключи

- Алгоритм: **RSA-3072 / SHA-256 / PKCS#1 v1.5**.
- `latest.json.sig` — **сырые 384 байта** RSA-подписи, не Base64 и не текстовый контейнер.
- Подписываются точные байты окончательного `latest.json`; клиент проверяет те же скачанные байты без повторной сериализации, изменения BOM или переводов строк.
- Публичный ключ встроить в приложение и установочный helper. Для .NET Framework 4.8 допустим встроенный публичный XML-ресурс RSA; экспорт для передачи на VPS — публичный PEM SubjectPublicKeyInfo. Оба представления должны соответствовать одной паре ключей; преобразование проверить тестом.
- **Закрытый ключ хранить на машине сборки вне VPS, репозитория, staging-каталогов и релизных архивов. Серверному ассистенту его не передавать.** Способ защищённого хранения и резервного копирования определить до генерации. Пароли не помещать в код, аргументы команд или журналы.
- До создания новой пары установить, существует ли уже согласованная пара; не заменять ключ незаметно. Ротация доверенного ключа требует отдельного плана.
- Подпись метаданных и Authenticode — разные механизмы. Текущие релизы не имеют Authenticode; наличие сертификата подписи кода остаётся неизвестным. Согласовать политику Authenticode отдельно, не подменяя ею обязательную RSA-проверку метаданных.

### Этап A. Проверка манифеста и версии

Предлагаемые файлы: `src/UpdateMetadata.cs`, `src/UpdateVerifier.cs`, `src/UpdateClient.cs`, публичный ресурс `assets/update-signing-public.xml`, тесты `tests/UpdateTests.cs`.

- [ ] Сначала добавить тесты: корректная подпись, изменённый JSON, неверный ключ, подпись неверной длины, повреждённая подпись, неизвестная схема/платформа/appId, неверные типы и размеры, текущая/старая/новая версия, HTTP-ошибки и отмена.
- [ ] Встроить доверенный публичный ключ; не принимать новый ключ из манифеста или с VPS как основание доверия.
- [ ] Получать JSON и подпись отдельным HTTPS-клиентом с обычной проверкой TLS; не передавать HWID, ссылки подписок или учётные данные пользователя.
- [ ] Ограничить размер манифеста, длину описания, время запросов и число повторов. Начальный ориентир для JSON — 256 КиБ; окончательные лимиты закрепить в коде и тестах.
- [ ] Проверять RSA-подпись до использования полей манифеста. Разбирать JSON только после успешной проверки.
- [ ] **При несовпадении подписи заново скачивать оба файла — JSON и `.sig` — без использования устаревшей пары из кеша.** Предлагаемый предел — три полные попытки; затем понятная ошибка и запрет установки. Не продолжать с непроверенными метаданными.
- [ ] Проверять `schemaVersion`, `appId`, канал, ОС, архитектуру, требования среды и наличие installer-пакета.
- [ ] Сравнивать `version` численно с FileVersion приложения через `System.Version`; не использовать AssemblyVersion (в текущем проекте 0.0.0.0) или строковое сравнение. Не предлагать автоматический downgrade.
- [ ] Принимать пакеты только с согласованного origin и разрешённого пути `/releases/...`; отклонять другой scheme/host/port, userinfo, фрагменты, обход пути и перенаправления за пределы доверенного origin. Локальное имя файла формировать самостоятельно.
- [ ] Проверить работу при обычном выключенном VPN. `UseProxy=false` отключает HTTP-прокси, но не TUN/WFP. При оставшейся аварийной блокировке Kill switch показывать причину и существующее действие восстановления; не снимать защиту автоматически.

### Этап E. Комплект для VPS и порядок публикации

После отдельного разрешения на реализацию подготовить:

- [ ] Публичный RSA-3072 ключ в PEM и его публичный SHA-256 fingerprint для сверки.
- [ ] Подписанный `latest.json` с реальными версиями, описанием, размерами и SHA-256.
- [ ] Двоичный `latest.json.sig` — 384 байта.
- [ ] Финальный Windows x64 Inno Setup EXE, соответствующий манифесту.
- [ ] Portable ZIP для ручного скачивания, если он указан в манифесте.
- [ ] Краткую инструкцию публикации и контрольные суммы файлов комплекта. Закрытого ключа в комплекте быть не должно.

Серверному ассистенту сообщить:

1. Раздавать файлы через Caddy с доверенным HTTPS на согласованном origin `:8443`; не менять рабочий REALITY на `:443`.
2. Для JSON использовать `application/json`, для `.sig` — `application/octet-stream`. Метаданные должны перепроверяться без устаревшего кеша; версионные EXE/ZIP должны иметь неизменяемые URL.
3. Не изменять байты JSON после подписи и не включать динамическое сжатие пакетов. Поддержка GET/HEAD обязательна; Range желателен, если в клиенте реализуется возобновление.
4. Сначала выложить и проверить доступность всех пакетов, затем публиковать манифест и подпись как согласованный комплект. Возможную гонку между двумя запросами клиент обрабатывает повторным скачиванием обоих файлов и отказом при неподтверждённой подписи.
5. Сохранять предыдущие релизы. Закрытые ключи и пользовательские файлы в web-root не размещать. Публичный ключ на VPS служит для сверки; клиент доверяет встроенному ключу, а не скачанному.

### Приёмочные проверки

- [ ] Положительные и отрицательные криптографические тесты, включая подпись длиной не 384 байта и изменение одного байта JSON.
- [ ] Несовпадение JSON/подписи при публикации: повторное получение пары и окончательный отказ после лимита; установщик не запускается.
- [ ] Отказ при подмене origin/пути, неподходящей платформе, старой версии, неверном размере, SHA-256 и подмене файла перед UAC.
- [ ] Проверка и скачивание при выключенном VPN, недоступном VPS, проблеме DNS, неверном TLS-сертификате и оставшемся Kill switch.
- [ ] Отмена скачивания и UAC, нехватка места, занятые файлы, сбой остановки службы, отмена/ошибка установщика, необходимость перезагрузки.
- [ ] Реальное обновление установленной предыдущей версии на Windows 10/11 x64; сохранение всех профилей/HWID/настроек и запуск от исходного пользователя, включая ввод учётных данных другого администратора в UAC.
- [ ] Portable остаётся ручным обновлением. Проверить доступность кнопок клавиатурой, обе темы и минимальный размер окна.
- [ ] Первая версия со встроенным updater устанавливается вручную: 0.56 сама не умеет получать обновления. Описать этот первоначальный переход в README.
